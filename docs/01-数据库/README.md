## MySQL 与 Oracle 对比

|   **维度**   | **MySQL 单进程** | **Oracle 单实例** | **Oracle RAC 集群**  |
| :--------: | :-----------: | :------------: | :----------------: |
| **数据库数量**  |  可创建多个逻辑数据库   | 只能管理 1 个物理数据库  |  多个实例共享 1 个物理数据库   |
| **物理文件隔离** | 各逻辑数据库有独立数据目录 | 整个数据库的物理文件统一管理 |   所有实例共享同一套物理文件    |
|  **资源分配**  |  所有数据库共享进程资源  |  单个数据库独占实例资源   |    多个实例分摊数据库资源     |
|  **隔离级别**  |  逻辑隔离（权限控制）   | 物理隔离（实例级）或逻辑隔离 |   物理隔离（实例级）但数据共享   |
|  **典型场景**  | 企业多业务线共用数据库服务 |   单业务系统独立数据库   | 高可用、高并发核心系统（如银行交易） |
## MySQL vs Oracle 高可用方案对比

---

### 一、核心本质

> **MySQL = 多服务 + 多数据（数据层面高可用）**
> **Oracle RAC = 多服务 + 一份数据（服务层面高可用）**

- MySQL：靠**多份数据副本 + 复制**实现高可用，本质是**数据层面的冗余**
- Oracle RAC：靠**多个实例访问同一份数据**实现高可用，本质是**服务层面的冗余**

---

### 二、架构对比

| 维度 | MySQL | Oracle RAC |
|------|-------|------------|
| 数据文件 | 多份（各节点本地） | 一份（共享存储） |
| 实例数 | 一个主库 + 多个从库 | 多个实例 |
| 存储方式 | 本地磁盘 | 共享存储（SAN/NAS） |
| 缓存一致性 | 无需共享缓存 | Cache Fusion（实例间高速网络同步） |
| 切换体验 | 有中断（需手动/工具切换） | 对应用几乎无感知 |
| 数据一致性 | 异步时有延迟，可能丢数据 | 实时一致，已提交数据不丢 |

---

### 三、MySQL 方案演进

主从复制 → MHA → MGR → InnoDB Cluster（一条「数据副本」主线）

#### 3.1 主从复制（Replication）
- 主库写 binlog，从库 I/O 线程拉取 → relay log → SQL 线程重放
- 异步（默认，有丢数据风险）/ 半同步（至少一从库确认）/ 延迟从库（防误删）

#### 3.2 MHA（Master High Availability）
- 第三方工具，监控主库，自动选主、补齐日志、切换 VIP
- 30 秒内完成故障切换，不依赖共享存储

#### 3.3 MGR（MySQL Group Replication）
- 基于 Paxos 共识协议，多节点对等
- 事务提交需多数节点确认，强一致性，自动选主
- MySQL 5.7+ 原生支持

#### 3.4 InnoDB Cluster
- 官方套件：MGR（数据复制）+ MySQL Shell（管理）+ MySQL Router（智能路由）

---

### 四、Oracle 方案

**RAC（本地高可用）+ Data Guard（异地容灾）**

#### 4.1 RAC（Real Application Clusters）
- 多个实例同时访问同一份数据文件（共享存储）
- Cache Fusion：节点间通过高速网络同步数据块，避免磁盘 I/O
- 任一实例挂掉，其他实例继续服务，对应用透明

#### 4.2 Data Guard
- 主库 redo 发送到备库，备库应用 redo 保持同步
- 三种保护模式：
  - 最大保护（零丢失）
  - 最大可用（几乎零丢失）
  - 最大性能（可能丢少量数据）

---

### 五、数据丢失风险对比

#### 5.1 为什么 RAC 几乎不丢数据
- 数据只有一份，且实时落共享存储
- 实例执行 COMMIT → redo 写入共享存储 → 才返回"提交成功"
- 实例挂了 ≠ 数据丢了，数据在共享存储上，其他实例自动前滚/回滚恢复

#### 5.2 为什么 MySQL 有风险
- 数据分散，靠复制同步，存在**复制延迟窗口**：
  - **异步复制**：主库提交成功即返回，从库可能还没收到 → 主库宕机则丢数据
  - **半同步**：至少一从库确认，但极端场景（主从同时宕机/网络分区降级）仍可能丢
  - **MGR**：最安全，但网络分区脑裂、多数节点同时宕机仍有边缘风险

#### 5.3 反向优势：MySQL 多副本更抗「单机全毁」
- MySQL 数据在多台机器上都有副本，一台机器 + 磁盘全坏，从库还有
- RAC 依赖共享存储可靠性，存储坏了则 RAC 也扛不住
- Oracle 终极组合：**RAC（防实例挂）+ Data Guard（防存储挂）**

---

### 六、各方案优缺点快速总结

| 方案 | 优点 | 缺点 |
|------|------|------|
| MySQL 主从复制 | 简单、成本低 | 异步有丢数据风险，切换慢 |
| MHA | 自动故障切换 | 已停止维护，依赖 VIP |
| MGR | 强一致性、自动选主、原生支持 | 网络分区可能脑裂 |
| InnoDB Cluster | 官方一体化方案 | 架构较重 |
| Oracle RAC | 实例级故障透明、零数据丢失 | 贵、复杂、依赖共享存储 |
| Oracle Data Guard | 异地容灾、保护模式可选 | 切换较慢（手动/FSFO） |
| SQL Server Always On | 一体化、可读副本、无需共享存储 | 依赖 Windows 集群 |

---

### 七、Q＆A

**Q：MySQL 能不能像 Oracle 那样多实例共享一份数据？**
> 不能。MySQL 架构决定每个实例必须管理自己的数据文件，没有类似 Cache Fusion 的共享缓存机制。要实现类似效果只能通过中间件做读写分离或分库分表，但本质仍是多份数据。

**Q：Oracle 为什么需要多个实例？**
> 为了"永远不宕机 + 无限扩展"。多个实例访问同一份数据，通过 Cache Fusion 保证一致性，一个实例故障其他实例继续服务，实现无缝切换。
